# 可行性报告：让系统"先问清楚再回答"

生成时间：2026-11-21　　作者：张子瑞　　跑分与代码状态：`c2faab2`

## 一、先说清两件事

这份报告回答两个问题：

1. **能不能让系统在问题含糊时反问一句**（例：问"访问校园系统" → 反问"你指的是哪个校园系统？"）
2. **为什么现在问"访问校园系统"，答的却是"人员进校 / 访客预约"**，怎么改

两件事相关但不是同一个问题：第 2 件是"检索找错了资料"，第 1 件是"系统该不该先确认意图"。
**结论先放这儿：两件都能做。第 2 件是当天就能修的缺陷；第 1 件需要改检索层与前后端协议，建议分三期做。

## 二、现象与复现（第 2 件事）

## 三、为什么会答偏（三层原因）

**第一层，词的多义。**

| 词 | 含义 A | 含义 B |
|---|---|---|
| 访问 | 人进校园（访问=来访） | 登录系统（访问=接入） |
| 校园 | 物理校园（进校、参观） | 数字校园（校园网、系统） |

"访问 + 校园"这个组合，恰好同时落在两类文档的语种里，而**知识库里没有一份讲"校园网络 / 信息系统 / 一卡通"的制度**。

**第二层，知识缺口。**

`data/raw` 现有 12 篇里：讲人进校的有（入校办法、开放日活动方案），讲车进校的有（机动车办法），
讲"校外访问数据库"的有（图书馆办法第七条）。**没有一份讲学生怎么登录教务系统、校园网怎么开通、
一卡通怎么补办**。资料里没有，检索只能挑"最像的"——这就是人员进校那两段。

**第三层，机制默认"能答就答"。**

现在的闸门只问"有没有依据"，不问"依据对不对题"：

- 分数 0.6699 > 0.45 → 判有依据；
- 词面覆盖 1.0（三个词都在）→ 词面闸门也不拦；
- 提示词要求"资料只覆盖一部分就先答写到的部分" → 模型于是拿访客预约去解释"访问校园系统"。

一句话：**三道闸门挡的是"没依据"，挡不住"有依据但答非所问"**。上次"进校访问答成访问系统"是同一个病，
只是方向反过来。

## 四、第 2 件事怎么改（不需要追问也能改）

按性价比排，1+2 当天可做，3 需要产品确认：

| # | 改法 | 具体做法 | 代价 / 风险 |
|---|---|---|---|
| 1 | 补知识库 | 新增《校园网络与信息系统使用管理办法》（VPN 开通、统一身份认证、教务/一卡通入口、故障报修电话）。**这是根因**，没这份文件，任何调参都只能让系统更会拒答，变不出答案 | 需要真实制度文本；示例数据只能演示链路 |
| 2 | 加"实体词"同义词族 | `config/synonyms.yaml` 增加：校园网 ← 校园网络/校园WiFi/无线网；统一身份认证 ← 统一认证/账号登录；一卡通 ← 校园卡；教务系统 ← 教务/选课系统 | 纯配置，零风险 |
| 3 | 多义词 + 主题分散时降权或反问 | 当查询只由多义词构成（访问/系统/校园 全是 `_AMBIGUOUS_WORDS` 或泛化词），且 Top1 与 Top2 分差 < 0.05、且分属不同文档时，**不直接作答**：走第 5 节的澄清，或退化为"分两类各答一半 + 说明" | 需要新增判定与阈值标定，做不好会误澄清 |

补充一条 prompt 约束（低成本、立刻生效）：在 `answer_system` 里加一句
「**不得把"访问系统"改写成"人员进校"**；资料只覆盖另一种含义时，明确说明"资料里只有××，没有××"，
不要用相近资料代替」。这条能把"拿访客预约解释登录系统"这种替换挡掉一半。

## 五、第 1 件事：追问澄清的可行性

### 5.1 现在离"能追问"还差什么

已有基础（都不用重做）：

- **会话是有状态的**：`session/store.py` 有 `SessionManager`（`max_turns=6`、超长自动摘要）、`MemorySessionStore`；
- **问答是流式的**：`/chat/stream` 已经会发 `meta / token / retract / done / error` 几种帧；
- **前端有渲染处**：`index.html` 的 `handleFrame` 已按 `frame.type` 分发。

缺的是三样：**"要不要追问"的判定**、**一个新的事件类型**、**用户回答后怎么回填**。

### 5.2 三档方案

**方案 A：提示词层（半天，风险最低，效果有限）**

在 `answer_system` 里加规则：「若问题里的关键名词有多种合理解释、且资料分别支持不同解释，
先反问一句"你指的是 A 还是 B"，不要直接作答」。
优点：只改 prompt，不动协议。缺点：模型自己判断歧义，不稳定，且它反问后用户回答仍要靠自然语言再检索，
容易出现"答了但没落实"；不可度量。**适合先试一天看体感，不适合作为最终方案。**

**方案 B：检索层探测 + 新事件（推荐，2–3 天）**

在检索结果出来后、生成之前插一道"歧义探测"：

```
判定澄清的条件（全部满足才问）：
1. 查询命中 ≥1 个多义词（访问/通行/办理/系统/校园…），且去掉多义词后剩余实词 ≤1 个；
2. Top1 与 Top2 来自不同文档，且分数差 < 0.05；
3. Top1 的分数不是碾压级（< 0.72，即"很像但不铁"）；
4. 同一会话内澄清次数 < 2（防止来回问）
```

满足则跳过生成，直接返回：

```json
{"type": "clarify",
 "question": "访问校园系统" ,
 "prompt": "你说的更像是哪一类？",
 "options": [
   {"label": "登录/使用校园网或校内系统", "query": "校园网 统一身份认证 VPN 登录"},
   {"label": "校外人员进校办事/参观", "query": "外来人员 入校 预约"},
   {"label": "校园一卡通办理与补办", "query": "一卡通 补办"}
 ]}
```

前端把 options 渲染成按钮；用户点一下 → 用 `option.query` 重新走一次 `/chat`（带同一 session_id），
原问题作为上下文保留。协议成本很小：前端加一个 `clarify` 分支，后端加一个返回类型。

**方案 C：完整对话式澄清（1 周以上，暂不建议）**

会话状态机（待澄清 → 已澄清 → 回答）、多轮追问链、澄清历史写入摘要、按用户画像个性化候选。
收益是体验更顺，代价是要改 `SessionManager` 的结构与存储格式，还要重做多轮评测。**初赛前不做。**

### 5.3 关键技术难点（决定成败的三个点）

1. **怎么判"该问"而不是"该拒"**。现在只有"答"和"拒"两条路。加"问"之后要划三条线：
   有明确依据 → 答；无依据 → 拒；**有依据但落在多个互斥主题上 → 问**。第三条线的判据必须可解释，
   建议就用 5.2 那四条，并写进日志（`clarify_reason`），事后可复盘。
2. **问错了比拒答更烦**。必须设上限：同一会话最多澄清 2 次；用户不选（或直接打字）就按原逻辑走；
   连续两次澄清未果 → 直接拒答并给部门电话。这叫"澄清有保底"。
3. **澄清候选从哪来**。两种来源：① 知识库之外的人工配置（`config/clarify.yaml`：主题 → 候选问法与检索词），
   可控但需要维护；② 用 Top2/Top3 的文档标题自动生成（"你问的是《入校管理办法》还是《图书馆办法》？"），
   零维护但读起来生硬。建议：默认 ①，缺失时退回 ②。

### 5.4 怎么验收（不验收就等于没做）

沿用现有评测习惯，新增 `data/eval/clarify_set.jsonl`（约 15 题：多义词、泛化名词、跨主题混问），
指标三个：

| 指标 | 定义 | 目标 |
|---|---|---|
| 澄清命中率 | 该问的题里真的问了 | ≥ 70% |
| 误澄清率 | 本可直接回答却反问 | ≤ 10% |
| 二次成功率 | 用户选了候选后答对 | ≥ 85% |

同时给现有 36 题 + 24 题对抗集跑回归，**误澄清率必须为 0**（这些题不该被反问）。

### 5.5 工作量与排期

| 阶段 | 内容 | 人日 | 可交付 |
|---|---|---|---|
| 一期 | 方案 A 的 prompt 约束 + 第 4 节 1/2 项（补文件、补同义词）+ 对抗集加 `sense_confusion` 用例 | 0.5 | 今天 |
| 二期 | 方案 B：歧义探测 + `clarify` 事件 + 前端候选按钮 + `clarify_set` 评测 | 2–3 | 初赛前可做 |
| 三期 | 方案 C：会话状态机与多轮澄清 | 5+ | 初赛后再做 |

## 六、结论与建议

- **"访问校园系统"答偏，根因是知识库缺"校园信息化"这一块**，加上"访问/校园"都是多义词。
  最有效的动作是补文件（第 4 节第 1 项），其次是同义词族与 prompt 约束；调阈值没用。
- **追问澄清可行，而且不需要重写架构**：会话、流式、事件分发都已具备，方案 B 是在中间插一道
  "歧义探测 + 一个事件类型"，2–3 天可落地，并可用三个指标验收。
- **顺序建议**：先修答偏（今天），再做澄清（初赛前），会话状态机留到之后。
  理由：答偏是"错答"，澄清是"体验"；**错答比不追问严重得多**。
